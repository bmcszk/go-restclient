# GitHub mechanics via gh CLI (bmcszk auth)

## GitHub comment mechanics (gh CLI)
- Before dispatching ANY closed-issue work, CHECK: (a) issue closedAt + close reason, (b) the closing commit actually contains the fix (build+run it if cheap), (c) pre-existing `.beans/` scratch beans for the issue (`scrapped` usually = already done or deliberately dropped). Never re-implement a closed issue's fix. If you already posted a wrong fix-SHA comment, PATCH it into an explicit correction immediately — stale misinformation on the issue misleads the reviewer.
- NEVER `-X PATCH/POST /issues/comments/<id>` with -f body — that EDITS (overwrites) the existing comment instead of replying. Reply to an issue comment via POST /repos/{}/issues/<n>/comments; reply to an inline review thread via the Reviews reply endpoint (`/pulls/<n>/comments/<id>/replies`), and verify each reply id comes back (re-POST on 404 — reply POSTs 404 mid-loop sometimes).
- gh here is authed AS bmcszk — comments post under the user's login; treat bmcszk PR comments as user directives.
- /tmp body copies go stale after `gh pr edit` — refetch the live body before appending (gh pr view > file > append > edit); verify the edit landed via `gh pr view --json body` grep.
- gh API cannot change a PR's head branch (PATCH head= silently ignored). To rename a branch after PR open: push new branch name → open NEW PR → close old one with supersede comment → delete old remote branch → update any fix-SHA issue comments to the new PR number.
- Verify each reply POST with a follow-up GET — but GET the reply by its own id (`pulls/comments/<replyId>`), NOT `…/comments/<id>/replies` (that list endpoint 404s even when the reply exists; verified 2026-09-22 #58).
- AGENTS.md forbids `//nolint` — never emit one even when a linter (gochecknoglobals) fires on legitimate package-level tables; the lint config here already tolerates them (removing the nolint passes 0 issues). BINDING USER RULE: never add //nolint and never change lint config without explicit user consent — fix the underlying issue instead.
- Ponytail review catches scaffolding: user stripped version constant + ldflags + dedicated unit tests down to ONE BuildInfo function; prefer zero new test files when existing fluent CLI tests already cover the behavior.
- Local lint (go1.27 toolchain) misses findings CI catches (unnamed same-type results, complexity thresholds differ) — run `golangci-lint run` locally AND check the CI matrix before declaring lint-clean.
- Tag-push CI runs (`on: [push]` fires for tags) build with `Main.Version=vX.Y.Z` — any test asserting version output shape must hold for dev/devel/tag builds; assert behavior (exit 0, non-empty, no usage error), never a specific version source.
- CI WATCH (user hard rule 2026-09-22, applies ALL repos): after every push, poll `gh pr checks <n>` (or `gh run list --branch <b>`) until ALL checks terminal; any fail → `gh run view <id> --log-failed` → root cause → fix → push → re-watch. NEVER report "pushed" without CI verdict. Known trap: `on: [push]` fires for TAG pushes too; tag checkouts embed Main.Version=vX.Y.Z into buildVersion().
- gosec via securego/gosec action: `-exclude` takes ONE comma-separated list (repeated flags = last wins); no `-config` flag exists in gosec CLI; govulncheck-action installs @latest with GOTOOLCHAIN=local — use go-version-input: "stable" (x/vuln v1.8 needs go>=1.26). Exclusions documented in docs/gosec-exclusions.md (G404 faker-data RNG, G304 user-supplied CLI file reads).
- Badge row (README, verified 2026 research /tmp/badges_research.md): native workflow badges use FILE name + ?branch=master; Go Report Card is DEAD (sunset Jul 2026, badge renders "retired") — never add; Scorecard badge needs scorecard-action publish_results:true + id-token:write FIRST; codecov free for public, token optional; Security tab = native surface once SARIF lands on master (distinct category per tool).
- SHA-pinning gotcha: `git ls-remote` on an ANNOTATED tag returns the tag OBJECT sha, not the commit. GitHub runs it fine, but actions with anti-impersonation webhooks (scorecard-action publish_results) REJECT tag-object pins ("imposter commit"). Always peel: `git ls-remote <repo> refs/tags/vX.Y.Z^{}` and pin the peeled commit. Audit every pin the same way.
- Bumping CI actions: re-verify EVERY tool-installed-via-@latest in Makefile/workflows when runner Go versions change — @latest moved under us (gotestsum v1.13 needs go>=1.24, broke 1.21/1.22 matrix). Pin install tools to a version compatible with the OLDEST matrix Go.
- Codecov tokenless CI uploads REJECTED since ~2024 policy ("Token required - not valid tokenless upload") — either repo secret CODECOV_TOKEN or self-host: extract go tool cover total → shields.io endpoint badge JSON committed to gh-pages (no third party, no token). gh-pages push needs job-level contents:write; global contents:read overrides nothing.
- Coverage chasing via fluent tests: file-flow BaseURL joining is applyBaseURLIfNeeded (variables.go:291) — absolute-path request DROPS the base path (scheme://host only), relative request prepends full base; resolveWithBaseURL/joinURLPaths (client_url_utils.go) are direct-execute-only, unreachable from fluent tests (no public single-request API) — don't artificially export to cover them. Server-side capturedRequests[i].URL.String() is PATH-ONLY; use tracking/capturedURLSegmentAt for full-URL asserts. {{$randomPassword N}} in URL emits a benign 'unresolved placeholder' WARN from the URL stage before body substitution handles it.
- NEVER name a test file after the METRIC it chases (client_execute_coverage_test.go = grab-bag smell); tests live in DOMAIN files (client_execute_loop_test.go, client_execute_system_vars_test.go, client_execute_baseurl_test.go) and follow the domain naming convention (TestExecuteFile_With<Opt>_<Behavior>_ for option-driven, TestExecuteFile_Loop<Behavior> for loop). Adding coverage is a side effect; organization is by feature.
- Fluent DSL HARD rules (docs/fluent-testing-guideline.md, MANDATORY): ALL state in parts struct — NEVER local vars for clients/config (`httpClient := &http.Client{...}` then `aClient(WithHTTPClient(...))` = forbidden; add a fluent given-method like aTLSInsecureClient() that builds it inside parts). Single given chain, .and() at END of line, no helper-function calls outside fluent methods, no linter-appeasement `var _` blocks. DSL surface helpers live in fluent_parts_*.go files (core/ext/capture/validator/graphql/cookies_redirects) — when user says 'wtf' at a helper, check it against this guideline first.
- DSL helper placement: each builder lands in the `<domain>_parts_test.go` of the domain that owns it (cross-domain shared → parts_test.go); domain test files hold TESTS ONLY. When adding a helper mid-task, land it in the right surface file immediately — moving later by scripted slice-and-append is error-prone (over-deletion nearly dragged a test along).
- Dependabot gomod group bumps can rewrite the `go` DIRECTIVE (x/text ≥v0.23 needs go1.23, v0.42 needs 1.26) — green test matrix is FALSE comfort under GOTOOLCHAIN=auto (jobs silently download the newer toolchain); the check that catches it is gosec (container, GOTOOLCHAIN=local). Verify which dep forces the directive via proxy.golang.org `<mod>/@v/<ver>.mod` `go` line; fix = pin that dep to newest version whose go-line fits the module's support floor, restore directive, push to the dependabot branch (maintainer push allowed) — dependabot labels its branch branch, never merge on red gosec.
- Post-merge race: pushing to a branch AFTER its PR merged = orphaned commit (release.yml missed a merge by minutes). ALWAYS `gh pr view N --json state` right before pushing follow-ups; if merged, cherry-pick onto a fresh branch off master + new PR. Watch for this on EVERY PR you monitor: the user merges mid-session without announcing — `gh run list` entries titled with `(<N>)` on master are the tell (a workflow title ending in the PR number = that PR is already merged).
- CI freshness trap after pushing to a PR branch: `gh pr checks N` reports the OLD merge-commit's checks and the check-runs API lags behind (COMPLETED runs still listed with status != completed). Authoritative state = `gh run list --branch <branch>` (newest run for the new head SHA) + per-SHA `gh api repos/{}/commits/<sha>/check-runs` re-queried fresh, never a cached single poll.
- Revive sweeps for NEW files (the whole lint config applies on first CI run, not just your target rule): fuzz/bench test files in package `restclient` trip `testpackage` (repo convention = `restclient_test` everywhere; expose unexported funcs via `export_test.go` vars — that file name is the ONE internal-package test file the testpackage rule tolerates, it exists to publish unexported symbols to the external test package); cognitive-complexity >7 trips on fuzz bodies with loop+branches (extract assertion helpers taking the parsed value, never a bool flag — `flag-parameter` fires on control-coupling). Run `golangci-lint run ./...` on the FIRST commit of any new file, not after CI.
- Ponytail deletion pass on CI workflow PRs before calling them done: `gh release create <files>` already attaches the assets — a workflow-artifact upload step ships a second copy of the same bytes (delete it); single-use `env:` vars inline (setup-go accepts `go-version: go.mod` and reads the module's directive directly — no version constant to drift); release-notes strings built once, not assembled from fragments.
- Fuzz targets: repo lint forbids internal-package test files (testpackage) — unexported funcs fuzzed via export_test.go indirection (linter-whitelisted `var XFn = unexported`), fuzz file in restclient_test, helpers split out for revive cognitive-complexity ≤7, no bool params (flag-parameter).
- ALWAYS report the full PR URL to the user, never a bare `#N`.
- Always start a session on an open PR by fetching fresh comments (`gh pr view --json` + `pulls/N/comments`): stale assumptions about PR state ("still open", "rounds upcoming") produce wrong answers the user must correct.
